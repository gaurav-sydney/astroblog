# Blog hardening, increment 1: L1 and acceptance criteria

**Work package:** [FE-129](https://linear.app/fe-factory/issue/FE-129). Blocked by FE-130 (Gaurav: CI/CD go-live settings).
**Status:** L1 + ACs persisted 22 Nov 2026. **Awaiting Gaurav's approval. No build starts before it** (tests-first). The L2 depth is written after approval.

## Outcome

automationworker.io runs as a hardened, self-verifying delivery. Every change is gated to its risk and auto-deploys from a protected `main`. The site is discoverable and ready to share for monetisation. Each published post reaches the confirmed list once. Nothing that works today breaks.

## Baseline: must stay green (BL)

| Id | Holds | Gates |
| --- | --- | --- |
| BL-1 | The live site renders at 1280 and 390 px, the assistant boots, and the subscribe form posts to Brevo (double opt-in) | rendered, chat, contract |
| BL-2 | The committed `dist/` equals the source build | dist |
| BL-3 | No secret, token, account id or personal email in any tracked file (public repo) | hygiene |
| BL-4 | Every post is valid, unique, listed and readable by the assistant; internal links resolve | content |
| BL-5 | Brand CSS tokens equal `brand.json`; fonts load; contrast passes (waivers open, see OQ-2) | brand |

## Scope: increment 1 (each milestone ships a working slice)

- **M1: Clean up and go-live rail.**
  - Merge PR #1 into `claude/blog-launch`, then create `main` from it.
  - `git mv deploy/ci/deliver.yml .github/workflows/deliver.yml`, and point its push trigger at `main`.
  - Make `main` the default branch and protect it.
  - Result: a push or merge to `main` runs the change-type gates, deploys to Hostinger, verifies live, and rolls back on failure. Behaviour-preserving, because live already serves this content.
  - Depends on SUB-A (FE-130).
- **M2: SEO capability.**
  - A new `capabilities/experience/seo/` with `sitemap.xml`, an RSS feed and `robots.txt`.
  - Per-post `BlogPosting` JSON-LD plus `Organization`, an `og:image`, and Twitter cards.
  - Add `@astrojs/sitemap` and `@astrojs/rss`.
  - Add `seo` as a change type in `delivery.json`, with an `seo` gate that asserts on the built output.
- **M3: Newsletter broadcast (DP-033).**
  - Activate the deployed but inactive n8n broadcast-on-publish.
  - Run the `newsletter` gate in CI.
  - Send one idempotent broadcast to the confirmed list per published post.

## Gate scope (proportionate assurance)

The baseline (hygiene, dist, contract) always runs. Then, by change type:

| Change type | Gates added |
| --- | --- |
| content | content, rendered |
| brand | brand, rendered |
| seo (new) | seo, content |
| feature | content, brand, rendered, chat |
| newsletter | newsletter |

The full set runs only on pipeline changes and releases.

**Regression ratchet:** every defect fixed in this increment earns a permanent gate check. The FE-122 silent-chat gate is the pattern.

## Regression impact by milestone

- **M1** touches BL-1 to BL-5 only through the pipeline that runs them. With no source change they stay green by construction, and the first `main` run is the proof.
- **M2** touches BL-4. The `seo` gate is additive, and the `content` gate is unchanged. `og:image` assets are generated at build time or static, and carry no tokens (BL-3).
- **M3** touches BL-1 (the subscribe path). The broadcast is a separate n8n flow and the subscribe contract is unchanged. Check the subscribe path still passes after activation.

## Acceptance criteria

The Gherkin is in [`acceptance.feature`](acceptance.feature).

- **AC-M1:** a content-only push to `main` runs baseline + content + rendered only (not chat or brand), deploys, and verifies live. A forced live-check failure rolls back to the prior release.
- **AC-M2:** adding a post regenerates `sitemap.xml` and `rss.xml` to list exactly the non-draft set. Every post page carries valid `BlogPosting` JSON-LD and an `og:image`. The `seo` gate fails if any of these is missing.
- **AC-M3:** publishing a post sends exactly one broadcast to the confirmed list. Re-running the flow sends none.
